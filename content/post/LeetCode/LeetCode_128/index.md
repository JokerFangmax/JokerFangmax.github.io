# LeetCode 128. 最长连续序列

> 题目链接：[https://leetcode.cn/problems/longest-consecutive-sequence/](https://leetcode.cn/problems/longest-consecutive-sequence/)  
> 难度：中等  
> 标签：哈希表、并查集

---

## 1. 题目描述

给定一个未排序的整数数组 `nums`，找出**数字连续**的最长序列的长度（**不要求**这些数字在原数组中位置相邻）。

要求算法的时间复杂度为 $O(n)$。

举例：`nums = [100, 4, 200, 1, 3, 2]` 中包含的最长连续序列是 `1, 2, 3, 4`，长度为 4——注意它们在数组里完全不相邻，也不按顺序出现。

**数据范围：**

- $0 \le nums.length \le 10^5$
- $-10^9 \le nums[i] \le 10^9$

**示例：**

```
输入：nums = [100, 4, 200, 1, 3, 2]
输出：4
解释：最长数字连续序列是 [1, 2, 3, 4]，长度为 4。

输入：nums = [0, 3, 7, 2, 5, 8, 4, 6, 0, 1]
输出：9
解释：序列 [0, 1, 2, 3, 4, 5, 6, 7, 8]，长度为 9；重复的 0 不影响。
```

## 2. 思路分析

### 2.1 暴力：对每个数向上数

"以 $x$ 开头的连续序列有多长？"——从 $x$ 开始反复检查 $x+1, x+2, \ldots$ 是否在数组里，数到断档为止。答案取所有 $x$ 中的最大值。

检查"某数在不在数组里"本身是 $O(n)$，套上外层循环和反复的向上数，最坏 $O(n^3)$；把数组先装进**哈希集合 (hash set)**，单次存在性查询降到 $O(1)$，整体降到 $O(n^2)$——`[1, 2, 3, ..., 10^5]` 这样的数组会触发最坏情况：每个 $x$ 都向上数一长串，总步数约 $\frac{n^2}{2} = 5 \times 10^9$，超时。

症结在于**重复劳动**：计算"以 1 开头的序列长 4"时，我们顺路走过了 2、3、4，但外层循环轮到 $x = 2$ 时又会把 3、4 再走一遍。同一片地，被犁了很多次。

### 2.2 排序：先把"无序"变"有序"

排序后连续的数就物理相邻了，一遍扫描统计最长的"相邻差 1"段即可，$O(n \log n)$。

这能过（力扣实测不卡 $\log$ 因子），但**不满足题目 $O(n)$ 的要求**，而且需要处理两个细节：相邻元素**相等**时要跳过（否则段被打断），差一判断用 $a[i] - a[i-1] = 1$ 而不是 $a[i] = a[i-1] + 1$ 的写法时要小心相等情形。它是有价值的参照系，但我们还能更好。

### 2.3 哈希集合 + 只从"序列起点"开数：$O(n)$

回到 2.1 的浪费：以 2 开头的答案，其实**被包含在以 1 开头的答案里**。只有一种 $x$ 值得从它开始数：$x - 1$ 不在集合里——$x$ 是某段连续序列的**起点**，它的答案不包含在任何别人的答案里。

于是流程变成：

1. 全部数装入哈希集合（顺便自动去重，重复元素不再骚扰统计）；
2. 遍历集合中每个 $x$：若 $x - 1$ 在集合中，跳过（它不是起点，会被别人顺路数到）；
3. 若 $x - 1$ 不在，说明 $x$ 是起点，向上数 $x+1, x+2, \ldots$ 直到断档，记录长度。

**为什么这样就是 $O(n)$ 而不是 $O(n^2)$？** 关键在均摊：向上数的每一步都发生在"某个起点的专职计数"里，而**每个元素只会在唯一一个起点的计数中被打到**（元素 $y$ 属于且仅属于以 $y' = y - k$（$y'$ 是该段起点）开头的序列）。把所有起点的计数步数加总，恰是每个元素被数一次，总共 $\le n$ 步。加上外层 $n$ 次遍历和 $O(1)$ 的起点判断，总代价 $O(n)$。

### 2.4 操作流程（以示例演示）

`nums = [100, 4, 200, 1, 3, 2]`，集合 $S = \{1, 2, 3, 4, 100, 200\}$：

| $x$ | $x-1 \in S$？ | 是起点？ | 向上数 | 本段长度 | 当前最优 |
|-----|---------------|----------|--------|----------|----------|
| 1   | 0 不在        | 是       | 1→2→3→4→5 断 | 4 | 4 |
| 2   | 1 在          | 否       | —      | —        | 4 |
| 3   | 2 在          | 否       | —      | —        | 4 |
| 4   | 3 在          | 否       | —      | —        | 4 |
| 100 | 99 不在       | 是       | 100→101 断  | 1 | 4 |
| 200 | 199 不在      | 是       | 200→201 断 | 1 | 4 |

只有 3 个起点真的动了腿，非起点元素一次都没被扫；向上数走的总步数（3 + 1 + 1）加起来不超过 $n$。答案 4。

对比 2.1：暴力版本里 $x = 2, 3, 4$ 时分别还要向上数 2 步、1 步、0 步——这些步骤在"只从起点开数"版本里被整体豁免了。

## 3. 代码实现

```cpp
class Solution {
public:
    int longestConsecutive(vector<int>& nums) {
        unordered_set<int> s(nums.begin(), nums.end());   // 装入集合，自动去重
        int best = 0;
        for (int x : s) {                 // 遍历集合：每个不同的值恰好一次
            if (s.count(x - 1)) continue; // x-1 在场 -> x 不是起点，跳过
            int len = 1;                  // x 是起点，专职向上数
            while (s.count(x + len)) len++;
            best = max(best, len);
        }
        return best;
    }
};
```

几个实现细节：

1. **遍历集合而非原数组**。原数组里的重复值会导致 $x$ 被当作起点重复检查多次（值相同则判断结果相同，纯属浪费）；集合天然去重，每个值只过一遍。
2. **起点判断必须用 `s.count(x - 1)`**，这是整个算法复杂度的命门（见 2.3 的均摊论证）。少了这一行，代码依旧正确但退回 $O(n^2)$。
3. **`while (s.count(x + len)) len++`** 用 `len` 兼作偏移量，不需要第三个变量；断档即停，起点计数结束。
4. 空数组时循环不执行，直接返回 0，无需特判。

## 4. 复杂度分析

- **时间复杂度**：$O(n)$。外层遍历集合 $O(n)$（去重后 $\le n$ 个值）；内层向上数的总步数——每个元素至多在"自己所属段的那个起点"的计数中被访问一次——合计 $\le n$；每步存在性查询均摊 $O(1)$。总计 $2n$ 量级的哈希操作。
- **空间复杂度**：$O(n)$。哈希集合存全部元素。

方案对比：

| 方案 | 时间 | 空间 | 满足 $O(n)$ 要求？ |
|------|------|------|---------------------|
| 暴力 + 每次线性查找 | $O(n^3)$ | $O(1)$ | 否 |
| 暴力 + 哈希集合 | $O(n^2)$ | $O(n)$ | 否 |
| 排序 + 扫描 | $O(n \log n)$ | $O(1)$ 或 $O(n)$ | 否（但实测能过） |
| **起点判断 + 哈希集合** | $O(n)$ | $O(n)$ | **是** |

并查集 (union-find) 也能做：把 $x$ 与 $x+1$ 合并，最后查询每个元素所在连通块大小，同样近似线性（单次合并均摊 $O(\alpha(n))$，反阿克曼函数近似常数）。但代码量数倍于哈希解且渐进不占优，本题首选哈希集合。

## 5. 常见疑问

**疑问一：内层 `while` 是循环套循环，为什么不是 $O(n^2)$？**

"嵌套循环 = 平方复杂度"是个不可靠的直觉，正确工具是**均摊分析 (amortized analysis)**。本算法里内层循环的总步数不是 $n \times$ 平均步数，而是被"一个元素只属于一个段"这个结构性质锁死在 $\le n$：元素 $y$ 属于唯一一段，该段有唯一起点，所以 $y$ 只会在那一个起点的 `while` 里被 `count` 到。**判断嵌套循环的真实代价，看的是每个底层单元操作的总次数，不是缩进层级。**单调队列、并查集的复杂度论证同出此门。

**疑问二：起点判断为什么是查 $x - 1$ 而不是查 $x + 1$？**

对称的诱惑：只对"$x + 1$ 不在集合里"的元素（终点）向下数，复杂度同样 $O(n)$，方向等价。真正错误的是**两边都不查**（退化 $O(n^2)$）或者**判断写在插入前**（集合还没建全，起点误判）。此外注意判断必须在**完整集合**上做：边插入边判断是常见WA 来源，比如数组 `[2, 1]`——先插 2 时 1 尚未入集，2 会被误判为起点（虽然本题误判起点只是多做功、不破坏正确性，但会破坏复杂度保证的成立前提）。

**疑问三：重复元素、负数、大数值域要处理吗？**

- 重复元素：`unordered_set` 自动去重，`[0, 3, 7, ..., 0, 1]` 里第二个 0 根本不进入遍历，天然免疫；
- 负数：`-10^9 \le nums[i] \le 10^9` 对哈希集合毫无压力——哈希按值散列，不关心正负；
- 值域大：正因如此**不能**开布尔数组做桶（值域 $2 \times 10^9$ 直接爆内存），排序做值域压缩（离散化）可以，但那又回到 $O(n \log n)$。哈希表是"大值域 + 存在性查询"的标准答案。

```cpp
unordered_set<int> s(nums.begin(), nums.end());
for (int x : s) {
    if (s.count(x - 1)) continue;   // 不是链头，让链头去数
```

方法论一句话：**链式结构中，只让"头"发起遍历，成员躺平等被数**——把全局的重复探索责任收到唯一的发起者身上，均摊复杂度随之成立。
